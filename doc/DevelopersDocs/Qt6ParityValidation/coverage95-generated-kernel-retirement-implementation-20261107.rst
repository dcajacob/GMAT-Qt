Generated kernel retirement after confirmed unload
==================================================

Generated station, event, ephemeris and CK/SCLK file retirement now requires successful native unloading and confirms that no furnish remains before deleting or replacing the file. A shared inline helper treats already-unloaded and absent files idempotently, propagates runtime unload/deletion failures, and provides guarded nonthrowing retirement diagnostics for destruction. Failed runtime cleanup retains pending filenames/readers for retry; station and locator setup becomes unready before affected cleanup. ContactLocator releases its owned reader, IntrusionLocator retains runtime failure ownership until retry, and CK clock-file deletion follows writer finalization with a second native check. A detached CK writer copy no longer claims the source clock filename. Compilation only; active writer assignment, shared kernel leases and complete original lifecycle/scientific scope remain open, with no row or verification credit.

Owning-source findings and implementation
------------------------------------------

The owning-source review found unconditional file deletion after ignored UnloadKernel results in BodyFixedPoint, ContactLocator, IntrusionLocator, EphemManager and CK/SCLK writer paths. Following the native unload-status and child-recovery changes, ignoring a reported failure could remove a path still referenced by CSPICE or continue a replacement with an incomplete pool. This packet propagates actual failure and loaded-state postconditions at those destructive operations. It does not reinterpret a failed native unload as success merely because recovery happened to remove the requested file.

The new SpiceKernelFileRetirement.hpp contains inline helpers only. Unload returns for an empty name or an already-unloaded file, requires a reader for a nonempty name, calls the existing virtual native unload and checks both its status and subsequent IsLoaded result. Retire deletes only after that succeeds, accepts ENOENT for retry and reports other filesystem errors with the filename. TryRetire catches native, standard and unknown exceptions and guards its own logging so the helper is noexcept. This is not a claim that every surrounding writer/destructor/finalization path is noexcept. Existing native class layouts, virtual slots, parameter IDs and numerical equations are unchanged.

BodyFixedPoint clears generated-geometry readiness before required retirement and clears filenames/frame identifiers only after both file operations complete. Its body-binding invalidation marks initialization false before retirement. Failed filenames remain available to the existing partial-generation retry path. Diagnostic deleteSPK/deleteFK policies still retain disk files after successful unload. Destruction uses TryRetire for each owned generated file and independently releases local frames and the reader; a retirement failure no longer causes this cleanup path to delete the uncertain file or discard the local frame allocations by throwing through InvalidateBodyBindings.

ContactLocator initialization and retained-value rebinding mark the locator unready and retire its generated FK/IK files before clearing pending paths or replacing observer/worker/base bindings. Staged binding values are still prepared first. Failed cleanup leaves names available for retry. Destruction attempts both generated-file lists with guarded helpers and deletes its independently allocated reader, which the prior destructor leaked. Copy construction already prepares a NULL reader; source reader ownership is not adopted by this change.

ReleaseIntrusionKernels still attempts all distinct pending paths and preserves the first failure. It now uses checked retirement and rethrows before clearing filenames or disposing the runtime reader. Successful cleanup then clears metadata and deletes the reader. Initialization/assignment already mark readiness false; retained-value rebinding now does so before retirement and performs retirement before base reference mutation. The destructor retains its existing diagnostic boundary and explicitly disposes any reader retained by a cleanup failure. Failed file cleanup is reported rather than followed by unconditional removal.

EphemManager destruction combines native retirement and the deleteTmpFiles policy in one loop, removing the later unconditional delete pass. Its disabled append/reopen branch now requires both ephemeris and attitude files to unload before closing/reloading their writers. The existing non-SPICE file-removal path is retained; the known earlier non-SPICE build issue was not re-executed. Writer stopping/finalization and other owner operations retain their existing contracts and are not claimed fully exception-safe by this packet.

SpiceAttitudeKernelWriter checks native unload before replacing an existing CK output, and uses checked file retirement for deletion. SCLK extension checks that both SCLK and CK have unloaded before removing/recreating the clock file. AttitudeWriterCK destruction initially unloads without deletion, retains the clock file and a live interface through the low-level writer destructor, then rechecks native membership before deletion. This preserves the existing possibility of buffered finalization and clock reloading in that destructor. A prior unload failure leaves the clock file retained. The no-writer path uses a scoped interface and skips it for an empty clock name.

AttitudeWriterCK copy construction already set ckWriter to NULL but copied the source's sclkFileName. Destruction could therefore unload/delete the source clock despite owning no writer. The detached copy now starts with an empty clock name; creating its own native writer supplies its own generated path. This does not complete active assignment, which still needs coherent retirement and copy preparation, or the lower-level SpiceAttitudeKernelWriter handle/clock copy model. Those concrete ownership follow-ups remain explicit rather than being claimed as fixed by the constructor change.

All four build versions succeeded. They compile the native helper/callers and final CK destruction/readiness/copy-construction changes, with final hashes matching v4. No native retirement helper, writer, parser, model, GUI, kernel operation or mission was executed. XML parsing, source/hash consistency and patch applicability are static packet checks only; they do not qualify filesystem failure behavior, reinitialization, source-copy isolation or any scientific requirement.
