Remaining NASA GUI scope: feasibility and recommended work
============================================================

The useful next campaign is evidence recovery plus a finite set of missing
acceptance contracts. My planning estimate is approximately **80-83% of
requirements and 77-78% of historical operations** under the existing bounded,
source-versioned row accounting. This is an engineering judgment conditional on
admissible evidence, not a guaranteed percentage or formal NASA qualification.
The full original scope stays visible. No denominator is reduced.

This replaces the earlier recommendation to defer the entire NASA remainder
while finishing a bounded Linux handoff. It answers which remaining coverage
work is practical and worthwhile, rather than redirecting the project into
indefinite core review or another full regression replay.

Review basis and limits
-----------------------

Reviewed all 416 remaining requirement texts and 564 historical operation
identities, their recorded evidence gaps and prior coverage candidates. Used
selected current source, fixture, repair and retained-evidence records to
distinguish missing proof from missing features and superseded failures. The
backlog preserves every exact source key/fingerprint, original rationale,
operation/keyword, older evidence version, recommendation and closure gate.

This is a planning review, not a fresh assertion-by-assertion audit of every
proof, original private procedure or independent scientific oracle. No GUI or
backend tests were run. No application/core code, test assertions, traceability
manifest, coverage ledger or sealed handoff was modified. No new source-row
credit is assigned.

Current reference counts are 742/1,158 requirements (64.1%) and 1,803/2,367
historical operations (76.2%). These are different denominators. Neither means
that every GUI control, input domain, platform or scientific regime is qualified.

Do first: recover valid proof without repeating passing scenarios
------------------------------------------------------------------

The older ledger contains 183 requirement and 30 historical keys absent from
the later two-report handoff union. A preliminary check examined all 51 older
versions referenced by those candidates:

* All 204 recorded audit/report/receipt/mapping file identities matched their
  recorded hashes. Compressed originals were read without making duplicate
  snapshots.
* All 266 row/version occurrences were found with reported verified status.
* No available fingerprint differed. Twenty-five occurrences, representing
  thirteen distinct keys, predate report fingerprints and need the original
  mapping/source identity checked explicitly.

These checks establish that the proposed audit has retained inputs. They do not
establish that each recorded pass satisfies the complete original obligation.
The substantive audit must check assertions, actual expected results, full
conjunctions, exact source/runtime versions, immutable receipts and row identity.
Reject overbroad, incomplete or unavailable proofs. Historical source-version
credit and current-build qualification must remain separate. In particular, do
not rehash old time-related proofs to the repaired TimeSystemConverter.

Also audit H2012:R843/R844/R960/R961: Pluto and Uranus Apply/Controls. The older
body-control review retains strict scientific failures, but the later
body-local-state review records both original cases passing unattended and
visibly after the local-state/celestial-clone repair. Both also pass in the later
catalogue. Their complete original control/appearance/Apply proof conjunctions
were not credited in the old ledger. Audit those existing passes before doing
anything new; do not repeat the repaired cases merely to populate a mapping.

If every recovery candidate proves admissible, the accounting would reach
925/1,158 (79.9%) and 1,837/2,367 (77.6%). This is a conditional ceiling for this
batch, not a newly measured result. Source-version recovery alone would account
for most of the recommended percentage improvement.

Do next: useful acceptance contracts that can be built locally
--------------------------------------------------------------

The 37 requirement candidates divide into four concrete bundles:

* **Six VF13ad progress/report rows:** FRR!E294-E299. Reuse the repaired original
  final-report truth and Forward/Central scaled/unscaled contracts. Explicitly
  verify control values, desired/achieved constraints, cost and iteration values
  in progress and per-iteration report files. Backward differences and the
  larger configuration heading are separate held rows. A residual alone is not
  a checked achieved/desired pair.
* **Four units rows:** All Others!E12/E14/E15/E16. Complete the applicable field
  documentation and km/km-per-second/degree input inventory, reusing hardware
  and force-field witnesses. Add only missing labels/documentation and
  unit-sensitive checks. The ambiguous non-dimensional-label sentence at E13
  is kept separate. Whole-input documentation remains a larger obligation than
  a few selected fields, so this bundle needs an inventory before execution.
* **Twenty-one metadata/query/summary rows:** All Others!E311-E326 and E331-E335.
  Make test type/platform, requirement linkage, truth/comparator/tolerance,
  comments/authorship/dates and platform/build eligibility explicit. Provide
  requirement-set and no-test queries, and qualify summaries that distinguish
  freshly executed, reused, skipped, interrupted, stale and failed evidence.
* **Six comparator/report rows:** All Others!E303/E304/E305/E307/E309/E330.
  Provide reusable position/velocity, file, numeric and OEM comparisons,
  configurable custom comparison, and an actual readable HTML export. Define
  units, tolerances, identity, missing/extra/nonfinite input and error behavior.
  Existing fixture assertions remain intact and authoritative.

Twenty-seven of these are acceptance-tooling requirements, not new GMAT GUI or
engine capabilities. They are worthwhile because the requested suite should be
reusable and explain its results. The other ten concern solver presentation and
units. Start with proof reuse and test/tooling changes; any actual GUI/reporting
repair needs a named failing contract and separate scrutiny. No new optimizer,
atmosphere, frame or integration algorithm is proposed by these bundles.

If all 183 recovery and all 37 local requirement candidates close, the result is
962/1,158 (83.1%). Historical recovery would remain 1,837/2,367 (77.6%). The
80-83%/77-78% planning range allows some candidate proofs to fail the substantive
audit, but it is not a statistical confidence interval or a lower bound.

Possible, but evaluate separately
----------------------------------

Nineteen requirement rows concern wider state/frame/body/attitude, parameter,
function-resource scoping and final-iteration ephemeris-output contracts. These
are scientifically useful, and I can prepare independent oracles and extend the
suite. Their universal wording, domain matrices and existing partial proofs make
them poor quick coverage targets. Define the missing matrix and reviewer first;
one additional passing circular/variable-only canary does not close an any-frame
or all-iterative-process contract. These nineteen are excluded from the main
forecast. Even their complete closure would add only about 1.6 percentage points.

Another 37 requirements are technically plausible separate projects:

* 26 non-MATLAB C client/ABI contracts, tested through a real external client.
* Six console/GUI parity and current Ubuntu artifact requirements. This host
  runs Ubuntu 26.04.1, but that observation is not console/GUI qualification.
* Two reusable SPK/TDM comparator contracts.
* Three legacy report-format requirements: actual XLS, TeX and their complete
  XLS/TeX/HTML parent. CSV or XLSX cannot substitute for literal XLS.

I would undertake these only for actual C-client, console or test-consumer needs.
They should not be added to GMAT or the harness simply to make a percentage
larger. Whole-product console parity remains broader than selected shared
missions, and C declarations alone do not prove an ABI/result contract.

What I would leave blocked, and why
------------------------------------

The 140 requirement rows outside the recommended/conditional/separate work are:

* 80 source conflicts, incomplete definitions or parent contracts dependent on
  unavailable/conflicted children. Examples include SPK-versus-CK attitude
  wording, OEM output time/frame options, event type/root-tolerance selection,
  all-commands headings, legacy parameter mutability, sampling-period-versus-skip
  wording, literal Vary/Achieve controls and incomplete function grammar.
* 45 external-component/data requirements: 38 MATLAB/fmincon-related and seven
  MarsGRAM/exact DE405-related. These include dependent headings. Compatible
  providers, licensed platform/toolbox and exact model/data identity must exist
  before actual integration/scientific verification.
* Twelve historical feature/platform decisions: four absent MSISE86 model/input
  requirements and eight old OS/platform headings or named targets. Restoring
  an atmosphere or supporting XP/Vista/Windows7/Leopard solely for historical
  coverage is not a reasonable default GUI task.
* Three CPU/RAM/performance requirements with literal Xxx placeholders. A test
  cannot supply the missing acceptance threshold.

The remaining 530 historical operations divide as follows:

* **151 missing named-fixture scopes:** EarthMoon, MercuryMoon, VenusMoon,
  Sarturn and named Barycenter body/member projects. A newly created Moon or an
  assumed Saturn alias does not establish the original identity/setup.
* **213 missing private-operation recipes:** unknown exit decision contexts,
  Name InputText values, ChangeAll programs, reference-rename/mutation sequences,
  full field tests and broad project suites. Many current equivalent mechanisms
  already have good bounded tests. More generic tests do not recover the unknown
  original values, ordering and expected results.
* **117 protected default clone/rename scopes:** current policy forbids the
  requested positive operations. Refusal tests are not positive clone tests.
* **46 source disputes:** 34 inconsistent operation/keyword/parent identities
  and twelve positive solver-nesting menu/interpreter conflicts. Preserve the
  disabled hypotheses and assertions; do not change engine semantics by guessing.
* **Three fmincon summary-suite scopes:** unavailable deployment plus missing
  detailed original procedures.

These are mutually exclusive primary blockers, not claims that a row has only
one problem. Recovering the NASA corpus or obtaining acceptance-owner decisions
could unlock substantial historical scope later. I cannot honestly forecast
those rows as executable now. Defining useful current-operation replacements
can improve the suite while the original NASA rows remain explicitly open.

Global acceptance gates remain separate
----------------------------------------

The machine-readable review routes every one of the 31 existing gap categories,
carries all 42 source-conflict records, all nine original replacement gates and
all 27 historical example dispositions. It retains the 97 changed core files
for scrutiny. CORE-FIRST's two-file author review and UTC repair are not
independent scientific approval of the accumulated core.

Practical Linux input/visibility/lifecycle checks, genuinely unexecuted supported
tutorials and one controlled final installed-artifact regression remain useful.
They should not be presented as increasing these source-row numerators by
themselves. Keep resizable non-fullscreen windows initially minimized; retain
logs/results and failure images, not new passing screenshot/binary collections.
Reuse existing passes during development and run the necessary final artifact
regression once after the implementation is frozen.

The current baseline and old ledger themselves contain bounded
current-operation equivalences. A stricter review against literal any/every
domain NASA obligations may reject earlier credits as well as proposed recovery
credits. Thus the forecast concerns the existing project accounting; neither
83% nor an eventual 100% ledger would alone establish full NASA qualification.

Execution decision
--------------------

Recommend the 217-row evidence-recovery audit first, ordered by retained proof
families, followed by the 37 local requirement contracts. For each package,
name the exact rows and missing evidence, maximum potential increment, core
impact and stopping condition before execution. Report actual accepted/rejected
proofs and newly verified rows; do not promise the conditional ceiling.

If a recovery proof is already complete and admissible, reuse it. If it is
partial, do not combine unrelated fragments or alter its assertions; run only a
named missing or affected obligation. If it depends on unavailable authority or
providers, leave it blocked and move to the next feasible bundle. Do not spend
another week repeating the same protected clone, ambiguous exit or nested-solver
rejection to chase its percentage.
